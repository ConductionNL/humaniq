# Design — time-attendance-mvp

## Context

hrmq records worked time only as per-period totals: `Timesheet` (`lib/Settings/register.d/hr-timesheet.json`, 0.3.0) carries `period`/`hours`/`status` with a full declarative submit→approve/reject/reopen lifecycle. There is no raw clock surface — no per-day record of when an employee started, stopped, or took a break — so Arbeidstijdenwet compliance (rusttijden, maximum dienstlengte, pauzes) is not checkable from data the app holds. The 2026-05-23 `spec/time-attendance` draft designed five schemas (clock-event, time-sheet, time-sheet-entry, time-allocation, availability-window) with kiosk/PWA/GPS/geofence channels, CAO toeslag matrices, and a payroll/pipelinq/planix export mesh. That draft predates round 1: at HEAD the `Verlof & verzuim` menu group (order 105), the `labour.json` corpus (6 rules, frameworks `bw7-10`/`nl-poortwachter`), the `Mijn HR` group with the `userId`/`@me` denormalisation pattern (mijn-hr-self-service), and `RuleAuditService`'s cross-type context indexes all exist. This MVP keeps the draft's core insight — clock data must be a first-class, auditable record — and drops everything that needs channels, jobs, or cross-app contracts.

Market grounding (verified 2026-07-12, Spectr `hrmq-insight-nc-ecosystem-gap`, `hrmq-insight-ranked-buildlist`): NL competitors all ship time tracking; the Nextcloud ecosystem has German ArbZG-oriented time-compliance apps but nothing covering the Dutch Arbeidstijdenwet. Statutory anchors (all `https://wetten.overheid.nl/BWBR0007671`): ATW art. 5:3 lid 2 (≥11 uur onafgebroken rusttijd in elke aaneengesloten periode van 24 uur; reducible to 8 uur once per 7×24h), art. 5:7 lid 1 (≤12 uur arbeid per dienst), art. 5:4 lid 1 (arbeid >5,5 uur → pauze ≥30 min; >10 uur → ≥45 min).

Verified at HEAD before designing:
- `x-openregister-calculations` operator vocabulary is `prop`/`+`/`-` over **numbers** (see `LeaveBalance.remainingHours` in `hr-leave.json` and openregister's `CalculationAnnotationValidator`) — there is no date-time parsing or duration subtraction, so `workedHours` from `clockIn`/`clockOut` is **not declaratively expressible**.
- `RuleEngine` predicates are `fn(array $object, array $context): bool`; cross-object facts reach a predicate only via `RuleAuditService`-built context indexes (`buildRelatedContext()` for PayrollRun/PensionFiling, `buildGlPostContext()` for `$context['glpost']`), loaded independently of the per-type loop and degrading to empty sets when a schema is absent.
- `RuleCatalogue` severity enum is `mandatory | conditional | recommended` — no `advisory`; one rule id emits one severity (the `NlVerzuimChecks` docblock records this exact lesson).
- `RuleCatalogue` glob-loads `lib/Standards/rules/*.json` and merges per-file `rules` arrays, so new rules in the existing `labour.json` need no registration; `RuleCatalogue::VERSION` (currently `2026-07`) must bump on any corpus change (SCHEMA.md).
- `NlAttendanceChecks.php` does **not** exist at HEAD — this change creates it.

## Goals / Non-Goals

**Goals:** a per-day `AttendanceRecord` clock record with an open⇄gesloten lifecycle; three versioned machine-checkable Arbeidstijdenwet rules (daily rest, max shift, break) with a `NlAttendanceChecks` provider and the cross-record context the daily-rest rule needs; attendance pages under the existing `Verlof & verzuim` group plus a `MijnAanwezigheid` `@me` page under `Mijn HR`; seeds exercising both violation branches; an explicit, documented boundary to `Timesheet`.

**Non-Goals:** kiosk/PWA/API clock channels, GPS/geofence/device fingerprints (own AVG/monitoring spec), CAO overtime/toeslag matrices (rulesets are configuration, ADR-001 rule 1), attendance→Timesheet aggregation jobs and payroll/pipelinq/planix exports (follow-up), weekly/16-week ATW averages and the once-per-7-days 8-hour rest reduction (period-window checks, not per-record predicates).

## Decisions

### D1 — One `AttendanceRecord` per employee per working day, not an event stream

The draft modeled four `clock-event` types (clock_in/clock_out/break_start/break_end) materialised nightly into entries. Without background jobs or kiosk channels in scope, the event stream buys nothing and costs an aggregator this MVP will not ship. `AttendanceRecord` collapses a working day to `clockIn`/`clockOut` timestamps + `breakMinutes` — exactly the fields the three ATW norms need. `date` (plain ISO date) is the working-day key, separate from the timestamps, so a night shift whose `clockOut` falls after midnight still belongs to one working day and index/filter columns stay plain. Corrections are plain object edits under OpenRegister's audit trail (the detail page keeps the audit-history tab); the draft's append-only correction-event chain tracks with the channels follow-up.

### D2 — `workedHours` is a stored field maintained by the writer; the checks never read it

`x-openregister-calculations` cannot express `(clockOut − clockIn) − breakMinutes` — the operator vocabulary is `prop`/`+`/`-` over numeric properties only (verified at HEAD; `LeaveBalance.remainingHours` is pure number arithmetic). So `workedHours` is a **stored** number the writer maintains (`(clockOut − clockIn in hours) − breakMinutes/60`, 2 decimals), declared with a description that says exactly that. Trade-off, stated honestly: a stored derivable field can go stale or be fat-fingered. Mitigations: (a) the ATW predicates compute shift length **from `clockIn`/`clockOut` directly** and read `breakMinutes` raw — a wrong `workedHours` can never mask or fabricate a violation; (b) `workedHours` is display/aggregation convenience (index columns, future timesheet roll-up), not compliance input; (c) no corpus rule checks `workedHours` consistency because that is app hygiene, not statute — the corpus stays universal law (SCHEMA.md). If OpenRegister later grows duration operators, migrating to a declarative calculation is a schema-only change.

### D3 — Daily rest is a cross-record check fed by a `RuleAuditService` attendance context

`nl-atw-dagelijkse-rust` compares **this** record's `clockIn` with the **previous working day's** `clockOut` for the same employee — RuleEngine predicates are single-object, so the sibling fact must arrive via `$context`, the exact mechanism pension-filing-upa-mvp introduced (`buildRelatedContext()`) and payroll-glpost-shillinq extended (`buildGlPostContext()` → `$context['glpost']`). Consistently with those: a new private `buildAttendanceContext()` in `RuleAuditService` loads all `AttendanceRecord` objects once per audit run and returns `$context['attendance'] = ['clockByEmployeeDate' => [employeeId => [date => ['clockIn' => …, 'clockOut' => …]]]]`, degrading to an empty index when the schema is absent (pre-import). The predicate for a record on date *D* looks up the same employee's record on *D−1 day*: if none exists, the rest period is ≥24h and the check passes; if it exists with a non-null `clockOut`, the gap `clockIn(D) − clockOut(D−1)` must be ≥11 hours. Only consecutive calendar days are compared — a free day in between trivially satisfies art. 5:3 — and the once-per-7-days reduction to 8 hours is deliberately not modeled (Non-Goals), which the rule statement says out loud so auditors know the check is the strict norm.

### D4 — Status is a minimal declarative open⇄gesloten lifecycle (warranted, barely)

Is a lifecycle overkill for two states? The judged answer: a **minimal declarative lifecycle is warranted**, on the SickLeaveCase gemeld⇄hersteld precedent — also two states, no guard. Reasons: (1) ADR-031's default for status fields is declarative `x-openregister-lifecycle`, and deviating needs a stronger reason than "few states"; (2) it feeds the manifest's `lifecycleActions` (Sluiten/Heropenen) so the detail page drives real guarded transitions instead of raw enum edits — the PayrollRunDetail `_note` rule (never render actions the backend does not guard) works in both directions; (3) `gesloten` gives the future aggregation follow-up an unambiguous "this day is complete" signal. What is deliberately **not** modeled: approval states — approval lives on `Timesheet` (D5); duplicating submitted/approved here would fork the approval surface. Transitions: `sluiten` (open→gesloten; the employee closes the day once `clockOut` is set — the description documents that the carrying write supplies `clockOut`/`workedHours`) and `heropenen` (gesloten→open; corrections). No guard class: closing your own attendance day is not a separation-of-duties event.

### D5 — AttendanceRecord is raw clock data; Timesheet stays the approval record; no automation between them

`Timesheet` = per-period (`YYYY-MM`) **approved** hours with the submit→approve lifecycle, `NoSelfApprovalGuard`, and downstream consumers (payroll, portaliq client review). `AttendanceRecord` = per-day raw clock facts, self-service, no approval. The seam is documented here and in both schema descriptions: an employee's attendance days *should* sum to the period's timesheet `hours`, and a future change may auto-derive or reconcile them — but that needs cross-object write hooks or an aggregation command hrmq does not have, the same reason leave-verzuim-mvp deferred posting `usedHours` from approved LeaveRequests. MVP ships zero automation: no roll-up, no consistency rule (cross-schema period arithmetic is beyond the corpus's single-object + context discipline as bounded today, and "should sum" is CAO/rounding-sensitive — flagged honestly rather than checked wrongly).

### D6 — Three ATW rules in the existing `labour.json`, new framework slug `nl-arbeidstijdenwet`

Leave/verzuim rules established `labour.json` as the labour-law corpus (`domain: labour`); working-time law is labour law, so the ATW rules join that file rather than opening a fourth corpus file — SCHEMA.md's one-file-per-sub-domain cut is domain (`labour`), and `framework` is the finer axis. `nl-arbeidstijdenwet` is a new framework slug (ATW is neither BW book 7 title 10 nor the poortwachter procesgang) and gets added to SCHEMA.md's framework examples list, as `nl-poortwachter` was. The pauze tiers (5.5h→30min, 10h→45min) live in the rule's `parameters.breakTiers`, read by the check from rule data — the `milestoneWeeks` data-over-code convention. All three rules `severity: mandatory` (single severity per rule id — the `NlVerzuimChecks` lesson; there is no advisory tier here anyway: an ATW breach is a breach). `RuleCatalogue::VERSION` bumps `2026-07` → `2026-07.1` — SCHEMA.md requires a bump on *any* corpus change and the month alone no longer discriminates (the July round already used `2026-07`).

### D7 — Placement: attendance pages under the existing `Verlof & verzuim` group; `MijnAanwezigheid` mirrors the Mijn HR pattern

The draft's own IA decision (SUB_PAGE under Verlof & verzuim, per ADR-001 rules 1–2: CAOs are rulesets not menus, approval queues are scoped actions not portals) survives modernisation: `AttendanceRecords` becomes a child of the now-existing `VerlofVerzuimGroup` — presence and absence are one attendance domain; no new top-level menu is invented, and final ordering of the ADR-001 menus stays owned by `hrmq-ia-navigation-alignment`. `MijnAanwezigheid` joins `MijnHrGroup` mirroring `MijnUren` exactly: index over `AttendanceRecord`, `filter: {userId: "@me"}`, own-data columns without `employeeId`, same route shape (`/mijn/aanwezigheid`). The `userId` property copies the round-1 denormalisation (a plain NC-user-id string, copy of the Employee's `nextcloudUserId`, because the manifest filter grammar cannot join across schemas — the `Timesheet.userId` description verbatim pattern). No `AttendanceApproval` queue page: there is no approval lifecycle to queue (D4/D5).

## Schema deltas

**`AttendanceRecord` (new fragment `hr-attendance.json`, `x-hrmq-fragment: hr-attendance`, version 0.1.0):** `employeeId` (string, format uuid, `$ref` Employee, required), `date` (string, format date, required — the working day the record belongs to, also for night shifts ending after midnight), `clockIn` (string, format date-time, required — ISO 8601 UTC, the fleet's `submittedAt` convention), `clockOut` (string, format date-time, nullable — null while the day is still open), `breakMinutes` (number, minimum 0, default 0 — total unpaid break minutes; input to the ATW pauze check), `workedHours` (number, nullable — **stored, writer-maintained**: `(clockOut − clockIn)` in hours minus `breakMinutes/60`, 2 decimals; description states the D2 rationale and that compliance checks never read it), `location` (string enum `kantoor`/`thuis`/`klant`/`anders`, nullable — where the day was worked; plain metadata, no GPS), `userId` (string, nullable — NC uid denormalisation, `Timesheet.userId` description pattern, drives `MijnAanwezigheid` `@me`), `status` (string enum `open`/`gesloten`, default `open`, required). `configuration` declares `x-openregister-lifecycle`: `field: status`, `initial: open`, `terminal: []`, transitions `sluiten` (open→gesloten; description: the employee closes the day, the carrying write supplies `clockOut` and `workedHours`) and `heropenen` (gesloten→open; description: reopen for correction — edits stay visible in the audit trail). Required: `employeeId`, `date`, `clockIn`, `status`. Gate-28: title + description on every property; the schema description names the D5 boundary to Timesheet. Register `info.version` 0.3.0 → 0.4.0.

## New corpus rules (labour.json)

| id | framework | source | statement (short) | severity | machineCheckable |
|---|---|---|---|---|---|
| `nl-atw-dagelijkse-rust` | `nl-arbeidstijdenwet` | ATW art. 5:3 lid 2 | After a working day the employee has ≥11 hours unbroken rest before the next working day starts: on consecutive calendar days, `clockIn(D) − clockOut(D−1) ≥ 11h` for the same employee (the once-per-7-days reduction to 8h is not modeled — strict norm) | mandatory | true |
| `nl-atw-max-werkdag` | `nl-arbeidstijdenwet` | ATW art. 5:7 lid 1 | A single dienst is at most 12 hours: `clockOut − clockIn ≤ 12h` (computed from the raw clock fields, never from workedHours) | mandatory | true |
| `nl-atw-pauze` | `nl-arbeidstijdenwet` | ATW art. 5:4 lid 1 | Work of more than 5.5 hours requires ≥30 minutes of break; more than 10 hours requires ≥45 minutes (`breakMinutes` vs elapsed `clockOut − clockIn`; tiers in `parameters.breakTiers`) | mandatory | true |

All three: `domain: labour`, `jurisdiction: NL`, `effectiveDate: null` (the ATW dates from 1996-01-01 — set `effectiveDate: "1996-01-01"` on all three; long-standing law, recorded for completeness), `sourceUrl: https://wetten.overheid.nl/BWBR0007671`. `parameters.breakTiers` on `nl-atw-pauze`: `[{"minHours": 5.5, "requiredBreakMinutes": 30}, {"minHours": 10, "requiredBreakMinutes": 45}]`. SCHEMA.md's framework examples gain `nl-arbeidstijdenwet`. `RuleCatalogue::VERSION` → `2026-07.1`.

Checks: `NlAttendanceChecks` registers the three predicates under object type `AttendanceRecord`. Vacuous-pass discipline (the `contractHoursPerWeek` precedent): records with a null `clockOut` pass `nl-atw-max-werkdag` and `nl-atw-pauze` (shift length not decidable while the day is open) and contribute no `clockOut` to the rest check; a record whose previous-day sibling is absent from `$context['attendance']` passes `nl-atw-dagelijkse-rust`. `RuleAuditService` gains `buildAttendanceContext()` (D3) alongside the existing context builders, wired in `audit()` exactly like `$context['glpost']`.

## Manifest delta

- **deepLink**: `AttendanceRecord` → `/apps/hrmq/attendance/{uuid}`.
- **Menu**: `VerlofVerzuimGroup` gains child `AttendanceRecords` ("Aanwezigheid", icon `ClockOutline`); `MijnHrGroup` gains child `MijnAanwezigheid` ("Mijn aanwezigheid", icon `ClockOutline`).
- **`AttendanceRecords`** (index, route `/attendance`): columns `employeeId`, `date`, `clockIn`, `clockOut`, `workedHours`, `status`; filters `status`, `location`; sort `date` desc.
- **`AttendanceRecordDetail`** (detail, route `/attendance/:id`): data widget "Attendance" (exclude `employeeId` — Related resolves the Employee, the fleet convention), related widget, `lifecycleActions` exposing exactly `sluiten` ("Sluiten") and `heropenen` ("Heropenen"), audit-history sidebar tab. No files widget (no document/retention field on the schema — the EmploymentContractDetail no-fabricated-leaves reasoning), no stat KPI (a single day's hours is not a headline aggregate — the LeaveRequestDetail precedent), no comms/calendar leaves.
- **`MijnAanwezigheid`** (index, route `/mijn/aanwezigheid`): `filter: {userId: "@me"}`, description "Jouw eigen aanwezigheid.", columns `date`, `clockIn`, `clockOut`, `workedHours`, `status`; sort `date` desc — mirroring `MijnUren` structure exactly.
- Manifest validates against app-manifest-v2 (`npm run check:manifest`).

## Risks / Trade-offs

- **Stored `workedHours` can drift from the clock fields** (D2) — accepted: checks read raw fields, the description documents the derivation, and the value is presentation/aggregation convenience. A future OpenRegister duration-operator makes it declarative with a schema-only change.
- **Daily-rest context loads all AttendanceRecords per audit run** — same O(objects) cost profile as the existing PayrollRun/PensionFiling/GLPost indexes, capped by `RuleAuditService::LIMIT` (10 000); fine at MVP scale, revisit with pagination if attendance volume explodes (365 records/employee/year).
- **Strict-norm honesty**: the rest check ignores the lawful once-per-7-days 8-hour reduction and the pauze check ignores CAO-pauze variations (art. 5:4 lid 2 collective-scheme deviations) — both rules *say so in their statements*, so a flagged violation reads as "breaches the default statutory norm", which an HR admin may justify. Over-flagging beats silently under-checking; refinement tracks with the CAO follow-up.
- **Night-shift date keying**: a shift crossing midnight keys on its start day (`date`), and the rest check compares consecutive `date` keys — two night shifts on consecutive dates compare correctly; exotic patterns (two shifts within one calendar day) are out of MVP scope and the schema description says one record per employee per working day.
- **Fragment objects go LIVE on import** (portal-schemas lesson): the seeds are obvious placeholders consistent with the existing hr-seed.json content.

## Open Questions

- None blocking. Attendance→Timesheet aggregation/reconciliation is the declared follow-up (D5); clock-in channels (PWA/kiosk/API) and GPS/geofence tracking (with its AVG/OR-consent spec) follow the draft's Phase-2 material; weekly/16-week ATW averages need a period-window audit facility first.
