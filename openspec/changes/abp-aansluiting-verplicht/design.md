# Design: ABP Aansluiting Verplicht

## Context

HRMQ currently integrates with `payroll-engine-nl` for generic UPA output and `employee-master` for participant data. However, ABP (the mandatory pension fund for Dutch public sector) requires ABP-specific UPA fields, premium calculations using a 36-hour full-time factor (not 40), VPL cohort tracking, partner pension registration, and five-day-maximum exit (Adieu) meldingen. Additionally, ABP publishes daily retour-berichten (confirmations and rejections) in CRS format with 247 fault codes, requiring an admin inbox and correction workflow.

The module bridges `payroll-engine-nl` (bruto salary, premiums) and `employee-master` (participant demographics, pension partner data) to generate ABP-compliant UPA monthly batches, handle retour-berichten, and track pension-partner life cycle changes.

## Goals

- **Regulatory Compliance**: Generate ABP-UPA records per UPA 2026.01 with ABP extensions, validate against ABP XSD, deliver monthly batches via SFTP by the 10th working day post-period.
- **Pension Participant Lifecycle**: Auto-enroll new hires, track deelnemeringsnummer (ABP-assigned ID), handle inter-agency transfers, and process exit meldingen within five working days.
- **Premium Accuracy**: Calculate ABP employer (22.5% 2026) and employee (4.5%) premiums using ABP's 36-hour FTE, franchise pro-rata application, and VPL-cohort-specific rates.
- **Partner Pension Compliance**: Register and maintain pension partners (spouse, registered partner, notarial cohabitation) with ABP; enforce partner registration as a prerequisite for partner pension accrual; handle termination per *Wet VPS* (divorce/death).
- **Retour-Bericht Triage**: Receive, parse, and display ABP return messages (Confirmation, Reject, Waarschuwing, Vraag) in an admin queue; enable correction and resubmission workflows for rejected UPA batches.
- **Workload Visibility**: Monthly and annual workload reporting by cost center and CAO segment, showing ABP premium burden and participant counts.

## Non-Goals

- Automatic VPL pension claim processing (out-of-scope; ABP handles VPL claims externally).
- Real-time integration with ABP APIs for participant master data (out-of-scope; participant data flows via UPA responses only).
- Multi-currency support (all ABP transactions in EUR).
- Retroactive historical UPA generation prior to implementation go-live (handled via manual correction process post-go-live).

## Key Design Decisions

### Decision 1: Entity-per-ABP-concept via OpenRegister

**Approach:** Each ABP concept (deelnemer, UPA record, retour-bericht, partner, Adieu melding, VPL) is a separate OpenRegister schema and register, not custom Eloquent models.

**Rationale:**
- Aligns with ADR-001 (data layer): ALL domain data → OpenRegister, NO custom Entity/Mapper.
- Enables cross-app reuse if other Conduction apps need ABP data (e.g., shillinq for bookkeeping GL posting).
- Built-in audit trail, versioning, multi-tenancy, RBAC per ADR-001.
- Schema-driven forms auto-generated by CnFormDialog, reducing custom UI code.

**Implementation:**
- Register: `abp-deelnemers` (schemas: `DeelnemerRegistratie`)
- Register: `abp-upa` (schemas: `UpaRecord`, `UpaVplBijlage`)
- Register: `abp-partners` (schemas: `PensioenPartner`)
- Register: `abp-retour` (schemas: `RetourBericht`)
- Register: `abp-adieu` (schemas: `AdieuMelding`)
- Register: `vpl-saldi` (schemas: `VplSaldo`)

### Decision 2: SFTP polling vs. webhook for retour-berichten

**Approach:** Cron-driven SFTP polling every 30 minutes (ABP publishes at 07:00 daily; polling interval captures any retransmissions same-day).

**Rationale:**
- ABP does not publish webhooks (only SFTP and REST; SFTP is primary, REST for partner mutations only).
- 30-minute polling ensures retour-berichten visible in admin queue within 1 hour of 07:00 publication, meeting SLA.
- Simpler than bidirectional SFTP heartbeats; less infrastructure than maintaining persistent SFTP connection.
- Conduction OpenConnector `abp-sftp` connector handles SFTP transport; HRMQ consumes via cron task `app:abp:poll-retour-berichten`.

### Decision 3: VPL cohort determination at schema level, not business logic

**Approach:** `DeelnemerRegistratie` schema includes `vpl-eligible: boolean` field, derived from `geboortedatum` at create/update time via a trigger in `ConfigurationService.importFromApp()`.

**Rationale:**
- VPL eligibility (born 1950–1972) is immutable per participant; persisting it avoids repeated date arithmetic.
- Enables fast filtering in reports and payroll UI without business-logic queries.
- If VPL rules change post-2026, the boolean can be recalculated as a repair-step migration.

### Decision 4: Premium tariff tables as OpenRegister configuration, not hard-coded

**Approach:** `AbpPremiePercentages` schema with fields: `year`, `regeling-code`, `werkgever-percentage`, `werknemer-percentage`, `vpl-percentage`, `franchise-bedrag` (EUR), `aov-percentage`. Loaded annually via `importFromApp()` in repair step or manual import.

**Rationale:**
- ABP publishes new percentages ~1 December for the following year; ConfigurationService handles version-driven import without code changes.
- Each loontijdvak references the tariff table row by year, ensuring correct premium rates even across calendar boundaries.
- Audit trail automatic per ADR-001; easy to verify in compliance audits.

### Decision 5: Adieu-melding as enqueued task, not immediate send

**Approach:** HR initiates Adieu-melding via UI form (`AdieuMelding` create). Form submission enqueues a background job `SendAdieuMeldingJob` with a 24-hour delay; salarisadministrateur is notified to verify the `eind-pensioengevend-loon` snapshot before auto-send. If not approved by day 3 post-`laatste-werkdag`, a second notification triggers auto-send (forcing compliance with 5-day window).

**Rationale:**
- Five-day window is strict; requiring HR to hand-verify eind-pensioengevend-loon before send prevents loon-calculation errors that ABP would reject.
- Two-tier notification (24h approval window, then auto-send by day 3) balances rigor with automation.
- Background job + OpenConnector `abp-rest` handle async delivery; retries automatic per job config.

### Decision 6: Correction flow as "UPA re-submission with correction-flag"

**Approach:** When a Reject retour-bericht arrives, salarisadministrateur corrects the underlying data (e.g., wrong loon in payroll), then clicks "Re-generate UPA" for that period. The system generates a new UPA record with `correction-flag = true` and `original-upa-record-id` cross-reference. ABP recognizes the correction flag and overrides the original.

**Rationale:**
- Prevents ad-hoc "manual correction files" outside the system; all corrections traceable to original reject reason and corrected loon values.
- Audit trail automatic: old UPA and corrected UPA both visible with reason-for-correction link.
- Matches ABP's UPA-mutaties workflow (rejects are fixed by submitting a new UPA, not a separate error-correction file).

### Decision 7: Partner registration via ABP REST API, not SFTP

**Approach:** `PensioenPartner` create/update/delete operations trigger a background job that POSTs to ABP's mijnabp-werkgever API v6.1 (`POST /partners`, `PUT /partners/{id}`, `DELETE /partners/{id}`). Response (success, pending, error) stored in `partner-registration-status` field.

**Rationale:**
- ABP REST API supports real-time partner registration and corrections (within hours); SFTP-only approach would require queuing partner changes until next month's UPA batch, risking stale partner data.
- Aligns with ABP's preferred modern integration path (REST for mutations, SFTP for bulk UPA).
- OpenConnector `abp-rest` connector handles authentication and retries.

## Entity/Schema Design

### DeelnemerRegistratie

Represents a single ABP participant.

**Fields:**
- `employee-id` (FK to employee-master, non-nullable)
- `abp-deelnemersnummer` (string, nullable until ABP assigns on enrollment)
- `aansluitings-datum` (date, non-nullable; typically `datum-in-dienst` or later)
- `deelnemingspercentage` (integer 0–100, default 100)
- `regeling-code` (enum: AP, KP, OP, VP, VPA, OP-ALT, AOV, TP, VT, WAO, ZW, WG)
- `partnerpensioen-keuze` (enum: `opbouw`, `uitruil-bij-pensioendatum`, `geen`)
- `arbeidsongeschiktheidspensioen-toepassing` (boolean, default true if age < 65)
- `vpl-eligible` (boolean, derived from geboortedatum; immutable post-create)
- `franchise-adjusted-percentage` (integer 0–100, for CAO-specific partial-membership; default 100)
- `created_at`, `updated_at`, `organisation_id` (per ADR-001 standard fields)

**Relations:**
- FK to `employee-master` via `employee-id`
- Has-many `upa-records` (monthly UPA batches for this participant)
- Has-many `pension-partners` (spouse/registered partner/cohabitation contracts)
- Has-one `vpl-saldo` (running VPL balance)
- Has-many `adieu-meldingen` (exit records, typically one final Adieu per career)

### UpaRecord

Represents a single participant's UPA submission for a payroll period.

**Fields:**
- `deelnemer-id` (FK to DeelnemerRegistratie, non-nullable)
- `loontijdvak-id` (FK to payroll period, non-nullable)
- `pensioengevend-loon-abp` (decimal EUR, non-nullable)
- `voltijdsfactor-abp` (decimal 0–1, non-nullable; uren / 36)
- `franchise-deel` (decimal EUR, pro-rated per voltijdsfactor)
- `premiegrondslag` (decimal EUR = loon − franchise)
- `werkgeverspremie` (decimal EUR, calculated)
- `werknemerspremie` (decimal EUR, calculated)
- `vpl-bedrag` (decimal EUR, 2.0% × premiegrondslag if VPL-eligible)
- `kp-flexibilisering-saldo` (decimal EUR, extra-inleg mutations or deelpensioen adjustments)
- `aov-premie` (decimal EUR, 0.4% in 2026)
- `correction-flag` (boolean, true if this UPA is a terugwerkende-kracht correction)
- `original-upa-record-id` (FK to prior UpaRecord if correction-flag=true)
- `status` (enum: draft, submitted, confirmed, rejected, corrected)
- `created_at`, `updated_at`, `organisation_id`

**Relations:**
- FK to `DeelnemerRegistratie`
- Has-many `retour-berichten` (linked confirmations, rejects, warnings)

### PensioenPartner

Represents a registered pension partner (spouse, registered partner, or notarial cohabitation).

**Fields:**
- `deelnemer-id` (FK to DeelnemerRegistratie, non-nullable)
- `partner-bsn` (string 9 digits, non-nullable; validated 11-proef)
- `partner-geboortedatum` (date, non-nullable)
- `samenwonings-datum` (date, non-nullable; huwelijk, registered partnership, or notarial contract date)
- `registratie-datum-bij-abp` (date, nullable; populated when ABP confirms receipt)
- `partner-registration-status` (enum: pending, registered, error)
- `einddatum` (date, nullable; set on divorce or death)
- `reden-einde-code` (enum: divorce, overlijden, separation; required if `einddatum` is set)
- `contract-scan-url` (string, nullable; file upload for notarial cohabitation contract)
- `created_at`, `updated_at`, `organisation_id`

**Relations:**
- FK to `DeelnemerRegistratie`

### AdieuMelding

Represents an exit melding to ABP.

**Fields:**
- `deelnemer-id` (FK to DeelnemerRegistratie, non-nullable)
- `laatste-werkdag` (date, non-nullable)
- `reden-uitdienst-code` (enum: 1–14 per ABP catalog; non-nullable)
- `pensioenopbouw-doorlopend-vlag` (boolean, true if participant is transferring to another ABP employer within 30 days)
- `eind-pensioengevend-loon` (decimal EUR, snapshot of final month's pension-bearing salary)
- `status` (enum: draft, pending-approval, scheduled, sent, confirmed, rejected)
- `scheduled-send-date` (date, typically 24h after `created_at`; auto-send by day 3 if not approved)
- `approval-status` (enum: pending, approved, auto-approved)
- `created_at`, `updated_at`, `organisation_id`

**Relations:**
- FK to `DeelnemerRegistratie`
- Has-one `retour-bericht` (ABP's Confirmation or Reject response)

### RetourBericht

Represents ABP's return message (Confirmation, Reject, Waarschuwing, Vraag).

**Fields:**
- `ontvangen-datum` (datetime, non-nullable)
- `type` (enum: Confirmation, Reject, Waarschuwing, Vraag)
- `gerelateerde-upa-record-id` (FK to UpaRecord, nullable if rejection is not batch-specific)
- `gerelateerde-adieu-id` (FK to AdieuMelding, nullable)
- `fout-code` (string, e.g., `ABP-PG-001`; nullable if type is Confirmation)
- `fout-omschrijving` (string, error description in Dutch)
- `verwerkings-status` (enum: open, in-behandeling, opgelost, gesloten-niet-oplosbaar)
- `correctie-upa-id` (FK to UpaRecord, populated once correction is submitted and confirmed)
- `created_at`, `updated_at`, `organisation_id`

**Relations:**
- FK to `UpaRecord` (if UPA-specific reject)
- FK to `AdieuMelding` (if exit-specific reject)
- Links to `UpaRecord` as correction once re-submission is confirmed

### VplSaldo

Running balance of VPL (Voorwaardelijke Pensioenaanspraak) per participant.

**Fields:**
- `deelnemer-id` (FK to DeelnemerRegistratie, non-nullable)
- `jaar` (integer, non-nullable; calendar year)
- `bedrag-tot-nu-toe` (decimal EUR, cumulative for year-to-date)
- `created_at`, `updated_at`, `organisation_id`

**Relations:**
- FK to `DeelnemerRegistratie`

## Reuse Analysis

The following OpenRegister services are leveraged per ADR-001:

- `ObjectService`: Create/read/update/delete for all six entities
- `ObjectService.findAll()`: List UPA records per period, retour-berichten per status
- `CnFormDialog`: Auto-generated create/edit forms for DeelnemerRegistratie, PensioenPartner, etc.
- `CnDataTable` + `useListView`: Admin queue table for retour-berichten with filter (status, fout-code, age)
- `ImportService`: Bulk import of ABP premium tariff tables annually
- `AuditTrailService`: Track all corrections, partner registration changes, Adieu status mutations
- `NotificationService`: Alert salarisadministrateur of Adieu approval window expiry, retour-bericht rejection, etc.
- `FileService`: Upload/storage of notarial cohabitation contract scans for partner registration

No custom CRUD, search, or form components are required.
