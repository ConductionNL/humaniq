# Learnings — review

---

## Consolidated Principles

These have been confirmed across multiple PRs or are explicit workflow rules. Promoted entries live in SKILL.md / references and have been removed from this list. Remaining entries cover situations not yet codified there.

- **GitHub review body update uses PUT, not PATCH**: `PUT /repos/{owner}/{repo}/pulls/{pull_number}/reviews/{review_id}` with `{"body": "…"}` — PATCH returns 404. Only works for submitted (non-pending) reviews with a `body` field change; the state cannot be changed via this endpoint.
- **CI/CD workflow trigger semantics require explicit before/after comparison**: when a PR replaces `pull_request: types: [closed]` + `if: github.event.pull_request.merged == true` with `push`, the gate changes from "a PR must exist and be merged" to "any push, including direct commits." Always compare old and new trigger semantics side by side, then evaluate branch protection (both classic API + rulesets) to determine whether the review gate survives the change. The three signals compound each other: `push` trigger + `secrets: inherit` + no branch protection = open secret exposure on any write-access push.
- **Docs-only OpenSpec PRs: workflow-conformance frame, not code-correctness**: when a PR only modifies `openspec/changes/` and `openspec/specs/`, the three blocker classes that recur are: (1) canonical spec at `openspec/specs/<name>/spec.md` shipped in the proposal PR — that artefact comes from `/opsx-archive` after implementation, not in the proposal; (2) `plan.json` shipped at proposal time — generated post-approval by `/opsx-plan-to-issues`; (3) PR title vs content drift, especially when the title names a parent project that the proposals/specs never reference. Make these the first checks on any spec-only PR.
- **Re-review APPROVE WITHOUT thread resolution leaves the PR un-mergeable.** ConductionNL repos enforce `required_review_thread_resolution: true` in their branch rulesets (development, beta, main). An APPROVE verdict flips `reviewDecision` to `APPROVED`, but unresolved threads block merge regardless. On every re-review where the verdict is APPROVE, the immediately-following step is to GraphQL-resolve every thread acknowledged in the verdict body — there is no "verdict body links → GitHub auto-resolves" path. Use `mutation { resolveReviewThread(input:{threadId:$id}){thread{isResolved}} }` per thread ID (fetched via `pullRequest.reviewThreads.nodes`); then assert `unresolved == 0` before reporting done. Observed twice: openregister#1423 (5 findings acknowledged at 10:53–11:00Z, APPROVE at 11:03Z, threads still unresolved until user reminder at 11:05Z); docudesk#135 (10 findings + 1 informational acknowledged in verdict body at 11:11Z, threads still unresolved until user reminder shortly after). Workflow checklist for re-review APPROVE: (1) submit APPROVE; (2) GraphQL-resolve every thread; (3) re-query `reviewThreads.nodes | map(select(.isResolved==false)) | length` and confirm zero; (4) THEN report done to the user.
- **Rollup/integration-branch PRs need source-PR redirection in the verdict**: when a PR is explicitly a "tracking/integration branch bundling N source PRs" (PR body says "do not merge"), every blocker the audit surfaces should name the canonical source PR it belongs to. Posting on the rollup is fine for the audit record, but the source PR is where the author actually iterates — call it out in the verdict body. Observed 2026-05-18 on openregister#1515 where 6 of 9 blockers traced to #1453 (live-updates) and #1469 (built-in providers).
- **Author-surfaced concerns in the PR body are findings already, not context**: when an author writes a "surfaced for maintainer judgement" section listing known-but-unfixed concerns, those items often ship merged unresolved. Treat the body's surfaced-concerns list as a verification checklist (post each one back as an inline finding with line-number-precise placement and the per-gate fix), not as "the author already knows so I can skip it." Observed 2026-05-18 on openregister#1515: 6 PR-body surfaced items + 3 new gate findings (SPDX, error_log, findAll OOM) all merged unaddressed.
- **Subagent line numbers need verification before posting**: the deep-analysis subagent on a 27K-line diff returned 4 plausible-but-wrong line numbers (NotifyPushListener.php:777 in a 457-line file; PermissionHandler.php:1077 vs actual :1088; MarkerLookupTrait.php:74 vs actual :83; LogDanglingLinkedTypes.php:138 vs actual :133). Always verify each finding's `file:line` is in a diff hunk via the `@@ -old +new @@` headers before building the JSON payload — a Python pass over the staged diff that prints `(newline, content)` for keyword matches is the reliable cross-check.

## Patterns That Work

- 2026-04-24: Spawning a subagent for analysis and passing the diff file path (not the raw content) keeps the main context clean and allows the subagent to explore specific hunks on demand. For diffs >50KB this is essential.
- 2026-04-28: When a PR enables a previously-dormant code path (e.g. fixing a JOIN that returned zero rows), pre-existing logic bugs in that path become live. Always check loop control flow (`break` vs `continue`) and null-guards in any code the PR's fix causes to execute for the first time.
- 2026-05-05: PR-level findings (title↔content drift, PR-description issues) don't have a sensible inline anchor. Post them as a top-level issue comment via `gh api repos/{owner}/{repo}/issues/{N}/comments` rather than forcing them onto a random file:line. Then link the issue-comment URL from the verdict body alongside the inline-comment URLs.
- 2026-05-05: Files in the GitHub `/pulls/{n}/files` API list ≠ files visible in `git diff`. A file with net deletions only (no `+` lines) is filtered out of the API but DOES show in `git diff` and may appear in mechanical-gate output. The 422 error message at posting time is "Path could not be resolved". Resolution: anchor the inline comment on a closely-related file that IS in the API list (e.g. `lib/Service/ActionService.php` instead of `lib/Controller/ActionsController.php` when only the controller is deletion-only) and explain the redirect in the comment body.
- 2026-05-05: For large security-sensitive PRs, dispatching a code-review subagent and a persistence-audit subagent **in parallel** (single Agent tool call with two invokes, both `run_in_background: true`) cuts elapsed time roughly in half vs serial. Brief each agent explicitly NOT to duplicate the other's scope — persistence agent on token / audit-trail / webhook / CI-secrets / lifecycle vectors; code agent on standard correctness + RBAC + injection. Overlapping findings on the same file:line are resolvable by consolidating into a single inline comment with both framings.
- 2026-05-05: When mechanical-gate findings overlap with the analysis agent's scope, instruct the agent explicitly NOT to re-discover them — feed the gate findings into the brief and ask the agent to focus elsewhere. Without this, you get duplicate findings on the same lines, and the gate findings drown in the inline-comment volume. Post mechanical-gate findings as a single dedicated top-level summary instead of one inline per gate hit (especially for high-volume gates like no-admin-IDOR with 185 hits where most are pre-existing-in-modified-files).
- 2026-05-05: Strict-mode reviews on PRs >300 files can produce 30+ findings. Cap the agent at ~20-25 inline comments and overflow off-diff findings to top-level issue comments — authors stop reading after ~30 inline notifications. The `REQUEST_CHANGES` verdict body still references every finding via markdown links, just not every line as inline.
- 2026-05-07: When a security PR's fixes use the body-level `requireAdmin()` pattern but keep `@NoAdminRequired` at the framework level, gate-9 (semantic-auth) will fire *more* after the fix than before — the security posture is correct (non-admins hit body, get 403) but the contract is encoded twice with the framework annotation now contradicting the body. Don't reverse the verdict; do flag it as a hygiene follow-up. The cleaner shape is per-method `@NoAdminRequired` removal on the admin-only methods, or moving them to a dedicated controller. Observed on openregister#1419 fix commits e1ba44c + 17facc5 + 45bbf86 — gate-9 went 1 → 10 hits.
- 2026-05-07: **Co-author concurrency**: when reviewing a PR you also have local push access to, expect the author OR you-as-co-author to push commits between Claude sessions. The "mystery reviews" with empty body and same author as the reviewer are GitHub auto-creating a `COMMENTED` review wrapper around each thread reply posted via `POST /pulls/{n}/comments/{id}/replies` — they're not unsolicited reviews. Cross-check by fetching `pull_request_review_id` on each comment via `gh api .../pulls/{n}/comments`; the wrapper review will have an empty body and one inline reply attached. This pattern lets you trace which session/process posted what.
- 2026-05-07: **Mechanical-gate override is a default, not absolute.** The protocol says "REQUEST_CHANGES if any protected gate fails" — but when you can demonstrate the gate is producing false positives or flagging pre-existing patterns the codebase explicitly tolerates (e.g. openregister's service-layer auth via PermissionHandler instead of body checks), it's reasonable to override to APPROVE with a verdict body that explains the override and files the gate-fix as a separate hydra-gates issue. Always ask the user before overriding; never silently bypass a protected gate.
- 2026-05-07: **Early-exit gate ≠ stop when the prior verdict is unflipped — and APPROVE alone doesn't resolve threads.** The re-review early-exit gate fires when there's no new activity since `LAST_REVIEW.submitted_at` — but if the prior verdict is still `CHANGES_REQUESTED` AND the reviewer's own prior reply comments have already marked every finding as resolved (e.g. "Resolved in <sha>" replies), the natural next action is to submit APPROVE **and** call `resolveReviewThread` for each thread, not to stop. The PR's `reviewDecision` only flips on a fresh APPROVE; thread `isResolved` only flips via the GraphQL mutation — neither implies the other. When asking the user, surface "Submit APPROVE + resolve threads" as the recommended option alongside Stop / Continue — DO NOT ask only "Stop / Re-review anyway" (loses the cheapest path) and DO NOT submit APPROVE without also resolving threads (leaves the PR sidebar with N unresolved threads even after the verdict flips). Observed on openregister#1437 (7 findings acknowledged-as-resolved via reply at 10:29Z, reviewDecision stayed CHANGES_REQUESTED until fresh APPROVE at 10:39Z) and openregister#1423 (5 findings acknowledged-resolved at 10:53–11:00Z; APPROVE submitted at 11:03Z but I forgot to resolve the 6 threads — user had to remind me; threads resolved at 11:05Z via batch GraphQL mutation).
- 2026-05-07: **CI workflow that fired the original blocker may no longer exist.** Before re-asserting a CI-status blocker on a re-review, check the active workflow files — a "Code Quality" workflow that produced a github-actions[bot] comment on the initial commit may have been deleted/disabled (`if: false`) since then. On openregister#1437, the original 🔴 about phpcs CI being red was based on a workflow run from a workflow file that's no longer in `.github/workflows/`. The substantive concern (missing `//end` comments) was still real and got fixed; the CI-failure framing was moot.
- 2026-05-07: **Sub-agent JSON-schema drift in batch reviews.** When spawning 11 parallel analysis agents with the same JSON output template (severity, title, file, line, body, finding_type), expect at least 6 different output shapes back. Common drifts: severity becomes `RED`/`CRITICAL`/`🟡 YELLOW` instead of `🔴`; body becomes split across `description` + `recommendation` (or `detail` + `action_required`, or `description` + `fix`); `file` becomes `component` or `location` (sometimes a multi-file string with `+`); `line` becomes `line_approx`/`lines` (sometimes a list, sometimes a range like `"1196-1210"`); top-level `verdict_recommendation` becomes `verdict`. A normalizer with regex extraction (line `\d+` from any string, file path from any path-like substring) plus a SEVERITY_MAP is mandatory before posting. Don't fight the drift; absorb it.
- 2026-05-07: **A "CI-not-running" blocker is load-bearing — fixing it can surface findings that were previously invisible.** On openregister#1357 F02 was a 🔴 about CI not running on the PR's branch shape (the workflow trigger excluded `platform-integration-*`). The author resolved it by merging `development` (which brought the trigger back into scope) — and the now-running CI immediately revealed two findings the prior review couldn't have caught: a license-allowlist failure on dompdf 3.1.5 (LGPL-2.1 not on the allowlist; `.license-overrides.json` had no entry) and ~30 phpcs violations including in the F03/F04/F06 fix code itself (named-parameter rule on `NotAuthorizedException()` calls, missing docblocks for new constructor params). Lesson: when a re-review shows the prior CI-not-running blocker is fixed, treat it as a NEW review surface — pull the fresh CI logs and inspect them as if it were a first review on those specific failures. Don't assume "F02 resolved → done."
- 2026-05-07: **A merge from base may remove files from the PR diff while leaving prior comments anchored to them.** On openregister#1357, composer.json was originally in the PR diff (F16 was a comment on it about dompdf). After the author merged `development` (which had already absorbed dompdf into composer.json), the PR's composer.json now matches development's exactly — `gh pr view --json files` no longer lists it. Replies to the existing F16 thread still work via the `/pulls/{n}/comments/{id}/replies` endpoint (GitHub keeps the thread anchored to its original location). New inline comments cannot be added to such files (the `POST /reviews` with `comments[]` payload would 422). When the right anchor for a new finding is on a file that's no longer in the diff, reply to a related existing thread (semantic continuity) or escalate to a top-level review-body finding — don't synthesize an inline on a different file.
- 2026-05-07: **A constructor-signature refactor in the production code is a cross-file blast: also flag the matching test.** On openregister#1357 the F06 fix added `IServerContainer` as the 9th positional, *required* arg to `AnnotationNotificationDispatcher::__construct()`. The test's `makeDispatcher()` helper still passed the pre-F06 positional shape with `null` in slot 9. PHPUnit was masked by the failing phpcs gate (PHPUnit `skipped` until phpcs `success`), so the test break stayed invisible across two review rounds. Lesson: when reviewing a constructor-signature change, *always* grep for `new <ClassName>(` in `tests/` and check that the test's positional shape still matches. Don't trust upstream gates to surface this — phpcs/eslint gating PHPUnit on the same job will hide the breakage. **Specific signal**: a PR that adds a *required* parameter to a constructor, even between two existing optional ones, is a near-certain test breakage unless the same PR updates the matching `*Test.php`.
- 2026-05-07: **A passing upstream gate can surface failures that were previously skipped — re-evaluate the whole CI surface on every fix commit.** On openregister#1357 the c34082ef commit was reported with `quality / PHPUnit (PHP 8.3, NC stable32) → skipped`. The 654fd2b9 commit fixed phpcs, which unblocked the PHPUnit job, which then showed `failure`. The PHPUnit failures had been latent since 535973c4a — they weren't *introduced* by 654fd2b9, but they were *first visible* on 654fd2b9. Don't read "newly failing job" as "this commit broke it" — diff the workflow's gating logic and check whether the prior runs were genuinely passing or just skipped/queued. Specific check: when a CI status flips from `skipped` to `failure` between commits, the cause is usually an upstream gate clearing, not a regression in this commit.
- 2026-05-07: **Diff `tests/` against `development` to attribute test failures correctly.** When a re-review surfaces a PHPUnit failure (`Too few arguments to function ::__construct(), 5 passed, 7 expected`), don't assume this PR's commits caused it. Pull both `lib/.../Foo.php` and `tests/Unit/.../FooTest.php` from BOTH `ref=development` and `ref=HEAD`, then diff. If the constructor signature is identical on both branches AND the test passes the same too-few args on both, the breakage is pre-existing on `development` — exposed by this PR's CI passing an upstream gate, but not introduced by this PR. Surface in the verdict as informational, not as a blocker, and recommend a separate `development`-targeted PR to fix it. Verified on openregister#1357 AuditTrailControllerTest.
- 2026-05-07: **A "representative example" inline comment can lull the author into fixing only the cited files.** On openregister#1357 my prior 🟡 phpcs comment listed `TransitionEngine.php:105/206`, `LifecycleGuardRegistry.php:53/57`, `AggregationRunner.php:145/146`, `Schema.php:1657` as a representative cross-cut of the ~30 phpcs errors. The author's follow-up commit (c34082ef) fixed exactly those 4 files and reported "phpcs now reports 0 errors across all four files" — but the same fix commit (535973c4a) had also introduced phpcs errors in NotificationHistoryController, RealtimeController, TransitionController, and Dispatcher that I hadn't cited individually. CI stayed red. Lesson: when a CI gate is failing across N files in the PR diff, list ALL N files in the inline comment (or post one comment per file), explicitly framed as "the full PR-diff scope per ADR-020." A representative subset implies the rest are out of scope. Closing line in such comments: "After fixing, please re-run the gate against the whole PR diff, not just the cited files."
- 2026-05-07: **Verify CI status from logs, not from author commit messages.** On openregister#1357, the c34082ef commit message claimed `phpcs --standard=phpcs.xml now reports 0 errors across all four files` and the PR's `phpcs` CI job still ran red on that commit. The claim was technically accurate (those 4 files were clean) but the gate scope is the whole PR diff, not the author's manually-selected subset. Always pull `gh api repos/{O}/{R}/actions/jobs/{ID}/logs` after a fix commit and grep for `FOUND.*ERROR|FILE: lib`, even when the commit message asserts the gate is clean. The mismatch between author-asserted-clean and CI-still-red is a strong signal that the author and the gate disagree about scope.
- 2026-05-07: **`dismiss_stale_reviews_on_push` auto-dismisses your prior REQUEST_CHANGES on every fix commit.** Development branch protection on ConductionNL/openregister has `dismiss_stale_reviews_on_push: true` in its ruleset's `pull_request` rule. So when the author pushes a follow-up commit between your reviews, `reviewDecision` flips from `CHANGES_REQUESTED` to `null` (not `APPROVED`) — your prior verdict is wiped. The inline comments stay (and stay marked resolved), but the PR sidebar reads "Review required" until you submit a fresh verdict. Watch for this: if `reviewDecision` is `null` on a re-review where you previously did REQUEST_CHANGES, it's not that the author resolved the threads — it's that the push dismissed your review. Always submit a fresh verdict on every re-review where there's a new commit.
- 2026-05-07: **For conflict-resolution merge re-reviews, grep at HEAD beats running the analysis sub-agent.** When the author pushed a fix commit + a merge with explicit conflict-resolution claims ("kept F03 RBAC gate", "kept F11 401 guards"), the verification target is binary: does each claimed pattern actually exist in the file at HEAD? Fetching each security-critical file via `gh api .../contents/{path}?ref=HEAD_SHA` and running targeted greps for the security patterns (`hasPermission`, `NotAuthorizedException`, `htmlspecialchars`, `userExists`, `@NoAdminRequired`, `IServerContainer`, etc.) verified all 14 fixes intact in ~5 batched bash calls. Spawning a fresh general-purpose sub-agent to "review the merge" would have been slower and more diffuse — the question wasn't open-ended analysis, it was pattern-presence verification.
- 2026-05-07: **GitHub secondary rate limit kicks in at ~55-60 content-creation calls in batch mode.** Posting 175 inline comments + verdicts across 11 PRs hit "secondary rate limit" mid-batch even with 0.3s sleep between calls. Recovery: 2s base delay + exponential backoff on the literal string `"secondary rate limit"` in the response, max 60s, 5 retries. Pattern: limit clears within 30-60s of pausing — it's about cumulative actions in a sliding window, not strictly per-second rate. Don't bother batching as a single COMMENT review (`POST /reviews` with `comments[]`) because one bad line aborts the whole review; per-comment posts via `POST /pulls/{n}/comments` survive partial failures. Each per-comment post creates a tiny `COMMENTED` review wrapper in the PR timeline — that's expected, not a bug.
- 2026-05-07: **`run-gates-on-pr.sh` silently false-passes when the base ref isn't fetched locally.** Step 5c's gates script does `git fetch origin "${BASE_REF}" >/dev/null 2>&1 || true`. When the fetch fails (e.g. base branch not present on the local clone — common for `beta`/`hotfix-*` if the operator only ever fetches `development`), `run-hydra-gates.sh --scope-to-diff --base origin/<base>` reports `0 changed file(s)` and ALL 14 gates pass — but only because the diff resolved to nothing. The exit code is 0 and the run-pr-review skill happily proceeds with a clean gate report. Defence: before running the gates, explicitly verify the base ref is fetched (`git rev-parse origin/<base>` should succeed) AND that the diff has the expected files (`[hydra-gates] Scope: diff vs origin/<base> — N changed file(s)` should match the `gh pr view --json changedFiles`). If they don't match, run `git fetch origin <base>:refs/remotes/origin/<base>` and re-run. Observed on openregister#1440: gates initially reported 0 files / all green, the real run reported 19 files / all green. Same outcome here, but a different PR could have masked a real protected-gate failure.
- 2026-05-07: **`hydra-gate-unsafe-auth-resolver` misses the `return true` variant of silent fail-open.** The gate documentation says it detects `catch (\Throwable) { return null; }` in auth/authorization/permission/role services. But the same anti-pattern with `return true` (preserving permissive legacy default on failure) is functionally identical for security purposes: a security-relevant resolver swallowing all exceptions and returning a permissive default. Observed on openregister#1440 `MagicRbacHandler::resolveInheritFromPublic` — `return true` flagged manually as a 🔴 blocker; gate stayed green. If the same shape appears across more code, the gate's regex should expand from `return null` to `return (null|true)` (and possibly `return ?$default`) — but only for genuinely permissive fallback values; `return false` and `return $deny` should stay clean.
- 2026-05-07: **`branch-protection / check-branch` is the canonical "wrong source branch" CI gate on ConductionNL repos.** It's a single required check on the beta branch ruleset that fails with `Pull requests to beta must come from 'development', 'main', or a 'hotfix/*' branch.` PRs from `feat/*` directly to `beta` always fail it — by design, to enforce the dev → beta → main promotion path. When this is the only failing required check, don't re-flag it as a code finding; just note it in the verdict body so the author knows the structural fix (re-target to `development`, or open a hotfix branch). The same check exists on `main`'s ruleset with stricter source rules.
- 2026-05-07: **DISMISSED prior review with empty body + no inline comments = treat as fresh review.** Observed openregister#1440 prior review id 4244034292: state `DISMISSED`, body empty, zero inline comments. Likely cause: ConductionNL's `dismiss_stale_reviews_on_push: true` ruleset auto-dismissed the prior review after the next commit (`cad0e3bf "Fix composer vulnerability"`), and the original review had no findings to begin with (an "ack" / "looks fine" with no body). The re-review early-exit gate doesn't fire (there IS a new commit), but there's nothing to anchor a re-review against — no thread replies needed, no resolutions to track. Path forward: skip Step 3's prior-comments fetch as a no-op, run Step 6 as a first review on the full diff, submit a fresh verdict (the `DISMISSED` doesn't carry forward).
- 2026-05-07: **PR-replaces-PR resubmissions are fresh PRs technically, focused re-reviews logically.** Observed openregister#1441 (resubmission of #1440 onto `hotfix/...` to satisfy `branch-protection / check-branch`). `gh api .../pulls/1441/reviews` returns `[]` — there are no prior reviews on #1441 itself, even though the author addressed each of my 7 prior findings on #1440 in a single fix commit (`6d18b508 "address PR #1440 review"`). The skill's Step 3 (re-review context) doesn't fire. Right pattern: brief the analysis subagent as *"verify each of these N prior findings is properly addressed AND scan for new issues introduced by the fixes"* with explicit per-finding fix-claim text from the previous review's verdict body, plus the fix-commit-window diff (`compare(prior_pr_head, new_pr_head)` — for #1440 head `cad0e3bf` to #1441 head `6d18b508` it was 11 files of intentional changes), not the full PR diff which mostly duplicates the original PR. Lead the verdict body with *"all N prior findings cleanly addressed"* before listing new findings — gives the author honest credit for the work. For #1441 the subagent's `prior_findings_status` JSON array (one entry per #1440 finding with `status: fully_addressed | partially_addressed | regressed`) was the cleanest output shape — copy that pattern.
- 2026-05-07: **Gate-14 (route-reachability) flags pre-existing missing routes when their containing file enters the diff.** Observed openregister#1441: `bash run-gates-on-pr.sh` reported gate-14 FAIL with 2 unrouted methods (`createMissingObjectFields`, `getObjectCollectionFields`) in `lib/Controller/Settings/ConfigurationSettingsController.php`. Both methods exist on `origin/beta` already (lines 319 and 350) — they predate the PR. The PR only changed the file's docblock for `updateRbacSettings` (the `@NoCSRFRequired` removal). Per ADR-020 ("gate scope is the PR diff, not the whole repo") this is a false positive — gate-14 should only flag methods *introduced or modified* by the PR, not every unrouted method in any file the PR touches. Defence at review-time: before treating a gate-14 fail as a real finding, `git show origin/<base>:<file>` and grep for the flagged method name. If it exists on base, it's pre-existing → out-of-scope. Worth filing a hydra-gate-route-reachability improvement to scope the gate's match to the diff hunks themselves rather than \"any method in a modified file\".
- 2026-05-07: **PR-body claim accuracy is its own finding category — separate from the underlying issue.** When a security PR claims *"All static analysis (Psalm, PHPStan, PHPCS) clean on changed files"* but the live `quality / PHP Quality (phpcs)` job is red, the framing matters: the issue isn't 5 trivial style errors (auto-fixable in seconds) — it's that the PR body misrepresents the CI state. On a security PR, honest accounting is load-bearing: future reviewers, audit trails, and post-incident forensics all rely on PR descriptions matching reality. Strict-mode 🔴 is appropriate here even though `phpcs` is non-required (so the CI override doesn't apply automatically). The comment body should explicitly frame it as "claim accuracy on a security PR", not as "fix the style errors" — that anchors the author on the right takeaway (proofread next time) instead of treating it as bikeshedding.
- 2026-05-07: **Stale-fetch hazard: re-fetch the head SHA at Step 8 immediately before posting, not only at Step 2.** Observed openregister#1441: my Step 2 metadata fetch returned `head_sha=6d18b508` and listed 9 commits. By the time my Step 8 COMMENT review posted ~22 minutes later (and the Step 9 verdict ~1 minute after that), the author had pushed `51220806` "phpcs auto-fix" at 14:10:57Z — addressing the exact 🔴 blocker I was about to raise. Both my reviews carried `commit_id: 6d18b508` and the verdict ended up calling out a finding that was already fixed on the actual head. The user had to point this out. **Defence**: between the analysis subagent finishing and the COMMENT review payload going out, re-run `gh api repos/{O}/{R}/pulls/{N} --jq '{head_sha: .head.sha, commits_count: ...}'` and `gh api repos/{O}/{R}/pulls/{N}/commits --jq '.[-3:]'`. If `head_sha` differs from the cached one OR commits list grew, fetch the new compare window (`compare(cached_head, new_head)`) and feed it back into the analysis brief as a delta-check pass — *"these N new commits landed since analysis started; verify each prior finding is still applicable"*. Then post against the new SHA. Cost of the extra fetch is one API call; cost of skipping is the embarrassment + an inline-edit / verdict-PUT cycle to retract a stale finding. **Recovery when this slips through**: edit the affected inline comment via `PATCH /repos/{O}/{R}/pulls/comments/{id}` with a "✅ Resolved in <sha>" header (keep the original body below for audit trail) and update the verdict body via `PUT /repos/{O}/{R}/pulls/{N}/reviews/{id}` (state cannot be flipped via this endpoint, only the body). Do NOT submit a new review just to flip from REQUEST_CHANGES to APPROVE — Strict-mode rules on remaining 🟡 may still hold the verdict, and the user may have explicitly asked for "no new review" exactly because of this constraint.
- 2026-05-07: **Re-review surfaces gate-7 IDOR in PRs whose prior review skipped mechanical gates.** Observed openregister#1273 (i18n PR titled `feat(i18n): Wrap bare strings…`): the prior review focused on translation-key correctness and didn't run hydra-gates. The re-review's Step 5c gate run found a NEW IDOR — `TasksController::allUserTasks` (newly added in this PR alongside an `appinfo/routes.php` registration of `GET /api/tasks`) is decorated `@NoAdminRequired` and accepts an `assignee` request parameter passed straight to `TaskService::getAllUserTasks()` with no guard. Pre-existing sibling methods `index/create/update/destroy` carry the same annotation but anchor authorization via `validateObject(register, schema, id)` from the URL — `allUserTasks` had no such anchor. **Lesson:** when a re-review is the first time gates run on a PR, treat protected-gate findings (5/7/8/9/10/11/12/13) as fresh-from-the-PR even if their narrow framing as "i18n" implies otherwise. Annotate the inline comment with provenance ("this finding surfaced from running mechanical gates in this re-review; the prior review focused on i18n contents only") so the author understands why it's appearing now and not earlier. - 2026-05-07: **Adding an RBAC gate inside a shared service method is a stealth regression for system-actor callers.** When the F04-style fix is to add `if (!$permissionHandler->hasPermission(...)) throw NotAuthorizedException;` inside a service method (here: `AggregationRunner::run()`), the controller path benefits — but every other caller of that service inherits the new auth requirement implicitly. - 2026-05-08: Class of bug — *port copies call sites but not the method definition*. - 2026-05-08: Adding a required constructor parameter to a service that has unit tests is a near-certain test-breakage signal. ## Mistakes to Avoid

- 2026-04-24: `line: null` in `GET /pulls/{n}/comments` does not mean a comment failed to attach. GitHub converts `line` to `position` internally. Verify by checking the comment ID exists, not `.line`.
- 2026-04-24: `gh api .../reviews --input file.json` returns `comment_count: 0` even when all inline comments land correctly — verify success by checking `.../pulls/{n}/comments` separately.
- 2026-04-24: Deleted integration tests replaced by a pointer comment are a regression risk. Always read the full context of removed test code — if a removed test covered a specific edge case, check whether that case is tested elsewhere.
- 2026-04-28: PHPUnit mock `method()->with($x)->willReturn($y)` silently returns `null` when called with a non-matching argument (no `expects()` set). A test configured `->with(self::UUID_CONSTANT)` but production code passing `getId()` (integer) returns `null` and causes a `TypeError` at `foreach(null)` — always verify mock expectations match the actual parameter type.
- 2026-04-30: When a REQUEST_CHANGES review is *dismissed* (distinct from being superseded by a fresh APPROVE), GitHub appears to auto-resolve the inline comment threads that belonged to it. Always fetch thread `isResolved` state after a dismissal before attempting to resolve threads manually — they may already be done. (Contrast with the consolidated rule that a fresh APPROVE does NOT auto-resolve threads — those still need an explicit `resolveReviewThread` mutation.)
- 2026-05-07: An author deferral of "outside this PR's scope" must be verified against the *file diff*, not just the change topic. Even when the PR title/description is narrow (e.g. "mail-sidebar fix"), the diff may add net-new methods elsewhere. On openregister#1285, two AuditTrailMapper concerns (`getProcessingActivities`, `findByIdentifier`) were initially deferred as "outside mail-sidebar scope" but turned out to be net-new methods (+90 lines) introduced by the PR itself. A prior /review-pr session accepted the deferral by replying in the author's voice — don't reply on behalf of the author, and always grep the file diff to confirm whether the cited code is pre-existing vs introduced.
- 2026-05-21: **jq backslash mangling in inline-comment payloads.** When a comment body contains raw backslashes (e.g. `LIKE '\_uuid%' ESCAPE '\'` referring to an SQL escape sequence in the reviewed code), piping through `jq -c '.comments[]' | while read | jq ... | gh api --input -` re-processes the JSON string and emits `jq: parse error: Invalid escape` mid-batch — silently skipping that one comment while neighbours succeed. Fix: write the full per-comment JSON to a file with `Write` (no jq round-trip), then `gh api -X POST .../comments --input /tmp/<name>.json`. The Write tool preserves backslashes literally inside JSON strings. Observed on openregister#1612 — the PG-asymmetry comment failed twice via jq before posting cleanly from a dedicated JSON file.

## Domain Knowledge

- 2026-04-24: ConductionNL/openregister has parallel SQL and PHP paths for RBAC: the SQL emitter (`applyRbacFilters`, `buildRbacConditionsSql`) handles the list endpoint; a PHP-side matcher (`ConditionMatcher`, `PermissionHandler`) handles find/single-object. Drift between these paths is the root cause of most list-vs-find inconsistencies.
- 2026-04-24: PHP's loose comparison coerces `null` to `""` (string) or `0` (numeric) for `<`, `>`, `<=`, `>=`. `null <= "2026-01-01"` returns `true` in PHP; SQL `NULL <= '2026-01-01'` returns NULL (filtered). Any comparison operator without an explicit null guard is a parity bug.
- 2026-04-24: PHP's array union operator (`+`) keeps the left-hand key on collision; `array_merge` overwrites with the right-hand value. Non-obvious precedence deserves a comment.
- 2026-04-24: SQL `col = NULL` (from `quoteValue('NULL')` in query builders) is always false/unknown — the correct SQL form is `IS NULL`. Pre-existing pattern in ConductionNL/openregister's SQL emitter.
- 2026-04-24: Symfony embeds Nextcloud route `requirements` verbatim inside named PCRE capture groups. A `^` inside a requirement anchors to mid-string and never matches — omit it. The pattern `(?!api(?:/|$)).+` is the correct form to exclude an API prefix.
- 2026-04-24: In ConductionNL/openconnector's `appinfo/routes.php`, all API routes use a lowercase `/api/...` prefix. A case-sensitive negative lookahead `(?!api(?:/|$))` covers all of them.
- 2026-05-07: **NC framework default for controllers is admin-required.** `@NoAdminRequired` is the explicit opt-out attribute. Methods that lack `@NoAdminRequired` are admin-only at the framework level via `SecurityMiddleware`, before any controller body runs. Recommendation to add `@AuthorizedAdminSetting('OCA\\<App>\\Settings\\<X>Admin')` is a *stronger* statement (also supports delegated admins) but requires a registered Settings class — non-trivial to add to a codebase that doesn't already use it. For first-pass reviews, the absence-of-attribute pattern is a valid admin-only enforcement mechanism; don't insist on `@AuthorizedAdminSetting` unless the app already uses it.
- 2026-05-08: Nextcloud apps express their license in three places that must agree — `appinfo/info.xml` `<licence>` element (this is what the NC appstore displays), `composer.json` `license` field, and the per-file `@license` PHPDoc tag. ConductionNL convention is `EUPL-1.2` everywhere. A PR that bumps `composer.json` to EUPL-1.2 and ships new files with `@license EUPL-1.2` headers but leaves `<licence>agpl</licence>` in `info.xml` is a license-declaration inconsistency, not a metadata typo — flag as 🔴, since the appstore signal contradicts the actual code license. Observed on opencatalogi#539.
- 2026-05-08: For Prometheus-style metrics endpoints and k8s health probes (`/api/metrics`, `/api/health`), the runtime caller (Prometheus scraper, kubelet, external uptime monitor) has no NC session. A controller method with only `@NoCSRFRequired` falls back to NC middleware's default = admin login required, so the endpoint silently 401s/redirects to the login page for the actual consumer. The reachable consumer (an admin's browser) is the one consumer that doesn't need these endpoints. Always check for `@PublicPage`/`#[PublicPage]` (or `@NoAdminRequired` if scoped behind a network ACL) on monitoring/probe routes — this is hydra-gate-5 territory but a manual reviewer can spot it from the route name + missing annotation alone. Observed on opencatalogi#539 (`MetricsController::index()` and `HealthController::index()`).

## Open Questions

- 2026-05-21: **`@NoCSRFRequired` is mandatory for any Nextcloud Controller endpoint called by external (non-browser) clients.** `passesCSRFCheck()` in `SecurityMiddleware` fires on ALL requests — regardless of HTTP verb — unless the method carries `@NoCSRFRequired`. External GIS tools (QGIS, ArcGIS), Prometheus scrapers, and ZGW API consumers authenticating via HTTP Basic Auth or OIDC have no Nextcloud session cookie and therefore no requesttoken, so every call returns a 403 `CrossSiteRequestForgeryException`. The existing project precedent: `MetricsController`, `HealthController`, and all `DrcController` ZGW-API endpoints already carry `@NoCSRFRequired`. When reviewing a controller that explicitly targets external consumers (doc-block or design doc says "Basic Auth / OIDC"), check this annotation first — it is the single most common blocker for externally-facing Nextcloud API endpoints. Observed on procest#483 (WfsExportController). Note: `@NoAdminRequired` and `@NoCSRFRequired` are independent annotations; a method can have one without the other.

- 2026-05-01: BREAKING CHANGEs that knowingly defer test updates ("integration tests deferred to a follow-up") create a pattern where development→beta merges always arrive with failing CI. - 2026-05-18: Inline-comment 422 "Path could not be resolved" when the file isn't in the PR's diff. - 2026-05-18: Sibling-new-file group completeness — when a PR fixes a pattern in one new file (e.g., extracts a modal from `ProhibitionIndex.vue` into `ProhibitionFormModal.vue`), check whether a parallel new file in the same PR has the same defect. Same-PR group completeness sweeps must cover NEW files, not just files-that-existed-before.
- 2026-05-18: RuntimeException-eats-403 pattern: when a controller has `} catch (InvalidArgumentException $e) { 400 } catch (Exception $e) { 500 }` and the service throws `RuntimeException` for an RBAC denial, the 403 turns into a 500 because `RuntimeException extends Exception`. Cross-check sibling endpoints in the same controller for the correct `} catch (RuntimeException $e) { 403 }` ordering — author may have applied it to one set of endpoints (standing-consent in DD #147) but not the parallel set (prohibition in same PR).

- 2026-05-21: Persistence-introduces-a-bypass pattern. - 2026-05-21: API-surface-vs-caller-wiring is a two-step concern.
